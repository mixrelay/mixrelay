# 작성·기여 절차

토큰·Core·소비자·스토리·문서를 같은 변경에서 갱신합니다. 현재 UI 패키지 버전은 <strong>{packageMetadata.version}</strong>입니다. 디자인 시스템은 이 제품 소스와 함께 관리하며 별도 패키지 버전이나 공개 배포 절차를 갖고 있지 않습니다.

## 채택한 공식 기준

| 공식 문서 | 채택한 방식 | MixRelay의 적용 |
| --- | --- | --- |
| [How to document your design system](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/) | 컴포넌트·토큰·조합·사용 규칙·기여 모델 | Foundations·독립 계약·Patterns/Pages·사용/주의·이 절차 |
| [Structuring your Storybook](https://storybook.js.org/blog/structuring-your-storybook/) | 시작 문서, 찾기 쉬운 분류, 설명·Playground·상태·조합 | Overview/Get Started, 역할별 Core/Feature/Screen 분류, 실제 args·고정 상태·제품 조합 |
| [4 ways to document your design system](https://storybook.js.org/blog/4-ways-to-document-your-design-system-with-storybook/) | Docs addon으로 실행 코드·API·사용 지침 함께 표시 | 저장소 안의 MDX와 Doc Blocks. API·상태·Canvas를 같은 계약에 연결 |

위 문서의 도구·플러그인·서비스 예시는 모두 도입해야 하는 목록이 아닙니다. 기존 `Core → Feature → Screen` 분류와 MixRelay의 팔레트·서체·밀도를 사용합니다. 예전 글의 `ArgsTable` 표기는 설치된 Storybook 10.5.10의 `ArgTypes`·`Controls` API로 적용합니다. 현재 공식 API 문서는 [Doc Blocks](https://storybook.js.org/docs/writing-docs/doc-blocks)에서 확인합니다.

## 변경 제안

| 기록 | 필요한 내용 |
| --- | --- |
| 문제 | 실제 과업·현재 사용처·재현 상태와 영향 |
| 기존 계약 | 재사용할 수 있는 토큰·Core·패턴과 부족한 부분 |
| 제안 | 추가/변경할 공개 속성·기본값·상태·토큰의 의미 |
| 소비자 | 영향받는 파일, 호출부 변경과 기존 동작의 호환성 |
| 근거 | 실제 사용례·키 실행·좁은 폭·긴 번역, 자동 검사와 미확인 범위 |

반복되는 의미 또는 실제 과업·접근성 요구를 근거로 Core를 확장합니다. 사용처 숫자만으로 승격하지 않으며 값 하나마다 새 토큰·컴포넌트를 만들지 않습니다. 특정 화면의 배치는 해당 Feature/Screen에 남깁니다.

## 구현 순서와 소유자

반복 UI 점검의 소스 목록은 `pnpm --filter @mixrelay/control-ui audit:ui`로 확인합니다. `--help`는 사용법, `--json`은 파일 생성 없이 구조화된 표준 출력을 제공합니다. 임시 검사 스크립트를 매번 만들지 않고 프로젝트 도구를 유지합니다. 목록의 레이블 표현식을 실제 계산된 접근성 이름·키 동작의 검증으로 해석하지 않습니다.

1. 제품 명세와 기존 독립 계약·소비자를 확인합니다.
2. 값은 `tokens.ts`, 표현은 theme, 공개 API·포커스·조작은 Core 소유 파일부터 바꿉니다.
3. Feature는 요청·응답·실패, Screen은 과업·배치를 같은 계약에 연결합니다.
4. `componentContracts.ts`의 목적·사용/주의·API·상태·토큰·소비자·테스트 경로를 갱신합니다. 공개 API 스냅샷은 소스와 AST로 대조됩니다.
5. 실제 CSF 스토리와 독립 MDX를 갱신합니다. Playground는 실제 Core의 `component`, 지원 `args`·`argTypes`, 고정 상태는 재현 가능한 초기값을 사용합니다.
6. Core 계약 관점과 제품 과업 관점에서 리뷰합니다. 결과는 <a href="/?path=/docs/design-system-review--docs" target="_top">Review</a>의 위치·관찰·영향·수정 형식을 사용합니다.

## 스토리 구성

| 종류 | 목적 | 작성 규칙 |
| --- | --- | --- |
| 설명 | 무엇을 언제 쓰는가 | 정확한 공개 타입, 기본값, 사용/주의, 실제 소비자 |
| Playground | 지원 속성을 직접 조작 | 실제 component metadata, 의미 있는 Controls. 금지된 외관 override나 제품 요청을 임의로 노출하지 않음 |
| 상태 | 특정 상태를 반복 재현 | loading·disabled·readOnly·invalid·selected 등을 독립 또는 실제로 지원하는 조합으로 고정 |
| 조합 | 여러 Core로 과업 수행 | 입력·제출·오류·복구 소유자를 명시; mock 응답과 실제 엔진 검증 구분 |
| play | 실제 동작 검증 | userEvent로 실행하고 역할·이름·값·포커스·호출 결과를 assertion. 이벤트를 장식용 로그로만 끝내지 않음 |

값을 소유하는 필드는 입력 이벤트를 상태에 돌려보냅니다. 값을 소유하는 Playground는 입력 중 Storybook preview의 로컬 상태를 사용하고 blur에서 `useArgs`로 Controls와 공유합니다. Controls 변경은 필드에 바로 반영합니다. 매 글자마다 비동기 Storybook 채널에 값을 맡겨 빠른 입력을 되돌리지 않습니다. 제품의 Feature 상태를 별도의 예시 구현으로 대체하지 않습니다.

## API·예시·코드의 대응

독립 MDX는 같은 CSF export를 Canvas로 렌더합니다. 단일 컴포넌트 metadata가 있는 경우 ArgTypes로 주요 속성을 표시하고, 정확한 전체 타입은 소스 대조 계약에서 확인합니다. 복사 가능한 Source 예시도 실제 CSF에서 가져옵니다.

우리 Canvas는 전역 환경 간섭을 피하기 위해 iframe으로 렌더합니다. 공식 Autodocs 매뉴얼에 설명된 제한에 따라 iframe Canvas 옆의 Controls가 예시를 갱신한다고 표시하지 않습니다. 속성 조작은 해당 Playground의 Story 화면에서 수행합니다. [공식 제한 설명](https://storybook.js.org/docs/writing-docs/autodocs)

## 완료 조건

```sh
pnpm check:ui-quality
pnpm --filter @mixrelay/control-ui check
```

빌드는 모든 공개 Core 계약의 실제 Playground export·렌더 소비·API·타입·기본값·소비자·테스트 경로·독립 문서·상태·고정 링크와 App/Screen의 Pages 목록을 검사합니다. 해당 변경의 실제 키보드, Light/Dark, 390px, 긴 번역과 오류 복구를 확인하고 `docs/validation/current.md`에 범위를 갱신합니다. 렌더·소스 coverage 통과를 실제 스크린리더·설치본·오디오 실행 성공으로 바꾸어 기록하지 않습니다.

## 호환성과 변경 기록

기본값·상태 의미·포커스·키 실행을 바꾸면 영향받는 소비자를 같은 변경에서 옮깁니다. 제거할 속성은 남은 호출부를 확인한 뒤 계약·스토리·문서를 함께 제거합니다. 변경 이유와 이전/이후 동작·검증은 리뷰 기록과 Git 변경에 남깁니다. 제품 진행 상태는 `docs/product.md`가 기준이며 별도의 진행 목록을 만들지 않습니다.
