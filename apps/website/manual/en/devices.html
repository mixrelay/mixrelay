MIXRELAY / MANUAL

Devices and virtual endpoints

Use MixRelay IO to exchange audio with other apps. Its device format is separate from the recording format.

Prerelease draft. Public downloads and purchases are not available yet. These instructions describe the current source build; installed behavior still needs verification in the environments noted below.

On this page

  • Choose the audio direction
  • Channels, sample rates and PCM
  • Processing buffers and latency

01

Choose the audio direction

MixRelay IO is the default virtual device. To receive audio played to it by another app, add it through Add node → Source → MixRelay Virtual I/O. This is Device → graph. To send a graph mix to an app such as OBS, add the device through Add node → Output → MixRelay Virtual I/O. This is Graph → device. In OBS or your DAW, select MixRelay IO as the audio input.

Connect the channels you need. MixRelay does not select a system default device or add a hardware monitoring route for you. For monitoring, add a physical output and connect the mix to it. The Driver also provides basic loopback from OS playback to capture without the editor’s graph mapping limits.

Removing a graph reference does not remove the virtual device. Licensed device creation is available through New virtual device. Removing a device from the status menu also removes its saved device settings; other apps using it lose that device.

02

Channels, sample rates and PCM

Open the virtual node’s Options to change Device name, Channels, sample rate and Bit depth. Only supported common settings are offered. Renaming requires a license. The status menu’s channel choices are 2, 4, 8, 16, 32 and 64; the underlying device supports 1–64 channels per direction.

On macOS, supported rates are 44.1, 48, 88.2, 96, 176.4 and 192 kHz. Device formats are Float32, PCM16, packed PCM24 and PCM32. Linux offers combinations supported by PipeWire. Physical devices follow their own capabilities. Internal DSP uses Float32; changing device bit depth does not change the WAV recording format.

A format change briefly interrupts audio. If it fails, check the message and the current value before retrying. A save failure can mean the device changed but its new settings were not saved.

03

Processing buffers and latency

The footer’s Processing buffer changes the engine’s I/O buffer when live changes are supported. Selecting a value applies it. On a recoverable error, Apply retries a supported setting. A smaller buffer can reduce buffer delay but may make dropouts more likely. Increase it if audio breaks up.

There is no separate buffer selector for each virtual device. Other apps choose their own client buffers. Buffer delay is the duration of one processing buffer, not total input/output latency. It does not promise a PipeWire-wide quantum. Multiple physical devices may require sample rate conversion and clock synchronization.

Application capture currently requires 48 kHz. The footer currently offers buffer control, not a processing sample-rate selector. Virtual-device rates are edited in the device settings. Some native plug-ins prevent live format changes because their preset state cannot yet be transferred.
