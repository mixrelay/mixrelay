# MixRelay UI 리뷰 관점

인물의 발언을 재현하는 역할극 대신, 공개 자료에서 확인한 원칙을 검토 기준으로 사용한다. 아래 질문과 적용 예시는 MixRelay의 해석이며 당사자의 제품 평가가 아니다. 제품 동작은 [product.md](../product.md), 구현 규격은 [디자인 시스템](../design-system.md)을 따른다.

## 디터 람스: 이해·정직·절제

[좋은 디자인의 원칙](https://www.vitsoe.com/us/about/good-design)은 유용성·이해 가능성·정직함·오래 쓰는 품질·세부 완결성을 강조한다. [1976년 강연](https://www.vitsoe.com/rw/voice/design-by-vitsoe)은 기능의 순서와 제품을 더 큰 체계의 일부로 보는 관점을 설명한다.

- 입력 → 처리 → 출력의 흐름과 채널 방향을 화면만 보고 읽을 수 있는가?
- Off가 신호 차단이고 Mute가 처리 유지라는 차이를 이해할 수 있는가?
- 선택한 그래프와 실제 실행 중인 그래프를 혼동하게 만들지 않는가?
- 연결 중·미설치·오류·명령 적용 대기를 정상 상태처럼 보이지 않는가?
- 장식·반복 설명을 줄여도 상태·단위·복구 행동이 남는가?
- 작은 글자·잘린 채널 이름·미세한 대비가 핵심 정보를 희생하지 않는가?

피한다: 여백만 늘려 정보가 사라지는 미니멀리즘, 모든 색을 없애는 정리, 복구 행동을 감추는 단순화.

## 조너선 아이브: 복잡성의 질서·하나의 조작 체계

[iOS 7 발표의 직접 발언](https://www.apple.com/newsroom/2013/06/10Apple-Unveils-iOS-7/)은 단순함을 복잡성에 질서를 부여하는 일로 설명한다. [Apple Watch 발표](https://www.apple.com/newsroom/2014/09/09Apple-Unveils-Apple-Watch-Apples-Most-Personal-Device-Ever/)의 Digital Crown 사례는 조작 중 내용을 가리지 않는 입력 설계를 보여준다.

- 처음 필요한 연결·레벨·녹음 동작이 가장 쉽게 발견되는가?
- 고급 옵션을 펼쳐도 대상 노드와 현재 값의 맥락이 유지되는가?
- 같은 기능의 버튼·툴팁·키보드·상태 전이가 화면마다 같은가?
- 노드 조작이 드래그·포트 연결·스크롤과 충돌하지 않는가?
- 조작 후 요청 대기·완료·실패·복구를 하나의 흐름으로 이해하는가?
- 좁은 화면·긴 번역에서도 조작 대상과 결과가 분리되지 않는가?

피한다: Apple의 색·유리 효과 모방, 아이콘만 남겨 이름을 숨기는 단순화, 맥락을 끊는 애니메이션.

## Teenage Engineering: 도구의 문법·조작 대응·탐색

[Jesper Kouthoofd 인터뷰](https://www.sfmoma.org/read/stay-curious-stay-naive-an-interview-with-teenage-engineering-jesper-kouthoofd/)는 제한된 형태·색의 규칙, 색의 의미, 손으로 익히는 조작과 탐색을 설명한다. [OP-1 조작 안내](https://teenage.engineering/guides/op-1/original/layout)는 색이 같은 인코더와 화면 요소의 대응을 구체적으로 보여준다.

- 녹음·입력·출력·경고의 색과 형태가 화면 전체에서 같은 의미인가?
- 앱 노드는 실제 앱 아이콘을 사용하고, 아이콘이 없거나 실패할 때만 fallback을 쓰는가?
- 레벨 제어 방향·단위·현재 값이 조작 직후 명확하게 대응하는가?
- 조밀한 노드에서도 반복 배치가 위치 기억과 빠른 조작을 돕는가?
- 클릭 영역과 포트 연결 영역은 작게 그린 모양보다 충분히 넓은가?
- 버튼과 미터의 피드백이 실제 동작을 설명하며 장식적 반응으로 오해를 만들지 않는가?
- 탐색은 취소·복구 가능하고, 녹음 중 설정 잠금과 실패 원인은 읽히는가?

피한다: 브랜드의 주황색·소문자·장난감 외형 복제, 전문 도구라는 이유로 작은 글자와 숨은 제스처를 정당화하기.

## 같은 화면을 보는 방법

예: 녹음 중 Record가 disabled인 화면. 람스 관점은 녹음이 계속 진행 중임을 정직하게 표시하는지, 아이브 관점은 Pause·Stop·완료 흐름이 이어지는지, TE 관점은 녹음 색·형태·조작 위치가 일관적인지 확인한다. 세 관점은 서로 다른 문제를 찾으며 취향 투표로 합치지 않는다.

먼저 제품 동작·접근성·데이터 보존·상태 진실성을 만족시킨다. 관점이 충돌하면 사용자 과업과 실제 화면 증거로 판단하고, 남는 시각 선택은 MixRelay가 결정한다.

## 결과 형식

관점별 최대 3개의 중요한 발견을 `위치 · 관찰 · 사용자 영향 · 수정`으로 기록한다. 이미지·스토리·실행 상태 등 확인한 근거를 붙이고, 미확인은 따로 표시한다. 적용할 문제가 없으면 한 줄로 쓴다. 출처의 주장과 프로젝트 해석을 구별하며, 같은 지적은 중복하지 않는다.

공통 확인: 키보드/focus, 색 외 상태 전달, 좁은 폭, 긴 번역, hover·active·disabled·오류, 실제 엔진 상태와 UI의 대응. 회귀 검사·Storybook 빌드·실제 설치본 동작 검증의 범위를 구별한다.
