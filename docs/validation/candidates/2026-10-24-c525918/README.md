## 원인과 수정

- Ubuntu ARM의 느린 coldplug로 mount 작업이 먼저 만료되면 실제 BOOT·UEFI 장치를 확인한 뒤
  이미지의 원래 mount unit을 다시 시작한다. fstab·검증 조건은 바꾸지 않는다.
  [7개 VM 부팅 검사](https://github.com/mixrelay/mixrelay/actions/runs/40067495800)는 모두 통과했다.
  이 실행의 Ubuntu ARM은 TCG에서 정상 부팅했으며 emergency 복구 분기의 실제 발동을 뜻하지 않는다.
- HAL은 CoreAudio의 `ProcessOutput`에서 렌더링한 클라이언트를 식별한다.
  `WriteMix`에서는 OS가 합친 PCM만 한 번 복사한다. 엔진 자체 출력 때문에 외부 앱이
  렌더링한 것으로 판단하거나, 외부 앱을 놓쳐 입력 지연이 바뀌는 문제를 막는다.
  호스트 입력 지연은 0, 앱에 보고하는 측정 지연과 변경 알림은 유지한다.
- 초기 그래프 조회 중 백그라운드 연결이 끊기면 복구 가능한 조회 실패를 503으로 전달한다.
  편집기의 기존 초기 조회 복구를 사용하며, 보안·프로토콜 오류와 변경 명령의 불확실한 실패는 유지한다.
  실제 소켓 단절 회귀, 데스크톱 테스트 230개와 기존 UI 조회 복구 테스트 31개가 통과했다.
- macOS의 첫 시스템 오디오 동의는 native AXPress로 한 번 승인하고 창이 닫혔는지 확인한다.
  소유한 신호 앱은 장치 구성 변경 알림으로 엔진이 멈춘 경우 같은 장치 UID를 확인한 뒤 재개한다.
  두 독립 소스의 실제 신호와 녹음 PCM을 검사하며, 무음을 이유로 신호를 다시 시작하지 않는다.
- 설치 UI는 실제 빈 그래프와 노드 생성을 확인한 뒤 연결한다. 업그레이드 상태 보존을 검사한 후
  UI fixture를 준비할 때는 편집기를 다시 열어 저장한 빈 상태를 읽게 한다.
  macOS의 증거 수집은 편집 창 안에서 조회해 Apple 메뉴의 Recent Items를 열지 않는다.
- Driver·녹음 변경의 재제출은 서버가 적용 전에 거절했음을 확인한 경우로 한정한다.
  같은 revision·그래프·녹음 상태를 다시 확인하며 불확실한 결과는 반복하지 않는다.

네 파일의 크기·SHA-256과 지원 계약 해시는 [후보 JSON](mix-relay.candidate.json)에 고정한다.
기본 엔진 48kHz·128프레임, PCM 누락·반복·손상·비유한 값 0 조건과 녹음의 채널·주파수 검사를 유지한다.
콜백 시각 진단은 I/O 종료 뒤에 출력하며 PCM 판정이나 실시간 경로를 바꾸지 않는다.

## 설치 시험에서 확인한 후속 실패

전체 실행은 macOS 15의 PCM·메뉴 실패를 확인한 뒤 중단했다. 후보 전체를 수락하지 않는다.
40080917787의 macOS 15 ARM은 새 설치 768프레임, 업그레이드 760프레임의 누락·손상으로 실패했다.
Intel의 새 설치는 8,128프레임 누락·384프레임 반복·23,104프레임 손상이었고,
업그레이드는 오디오가 통과했지만 Compressor 메뉴 선택이 완료되지 않아 그래프 검사가 실패했다.
자동 녹화 제거만으로 이 실패들이 해결되지는 않았다.
[앞선 전체 실행 40077859659](https://github.com/mixrelay/mixrelay/actions/runs/40077859659)의
macOS 14·26 ARM과 Linux x64 네 대상, Debian·Kali ARM은 새 설치·업그레이드·제거를 통과했다.
Debian·Kali ARM에서 실제 guest CPU 4개를 확인했으며 Debian의 종료 관찰은 각 구간 857~2,160ms였다.
macOS 15 ARM의 업그레이드는 1,908프레임 누락·손상, Intel의 새 설치는 2,124프레임 누락으로 실패했다.
두 CPU의 Apple 검증과 임시 네트워크 규칙 해제는 통과했다.
같은 실행의 Ubuntu ARM은 새 설치 전체를 통과했다. 업그레이드는 Add node 메뉴가 열리지 않아
출력 항목 조회가 실패했으며, 두 모드의 오디오·녹음·제거는 통과했다. 종료 관찰은 각각 약 4.7초·3.7초였다.
[이전 전체 실행 40076781600](https://github.com/mixrelay/mixrelay/actions/runs/40076781600)의
macOS 14 ARM과 Linux x64 네 대상은 새 설치·업그레이드·제거를 통과했다.
macOS 14 ARM에서 관찰자의 실제 접근성·화면 캡처
권한을 확인했고 노드·연결·무료 상태가 렌더링된 스크린샷을 직접 확인했다.

[측정 권한 진단 40074890715](https://github.com/mixrelay/mixrelay/actions/runs/40074890715)에서
macOS 15 ARM은 두 설치 모드와 제거를 통과했다. 새 설치의 측정 프로그램은 입력 권한 0에서
3으로 승인된 뒤 첫 I/O를 시작했고, 업그레이드는 기존 승인 3을 확인했다. 양쪽 PCM 누락·반복·손상은 0이다.
제품의 첫 동의 검사는 그대로 실행하며, 사전 오디오 재생·PCM 구간 제거·실패 후 재측정은 하지 않는다.

시험 도구는 제품 설치 전에 XCTest 관찰자를 한 번 빌드·서명하고 같은 코드 요구사항에 접근성·화면 캡처
권한을 준비한다. TCC 데몬의 교체 PID를 확인한 뒤 제품을 설치하며, 제품 실행 중에는 이 준비를 반복하지 않는다.
Linux 메뉴는 최신 접근성 상태에서 펼침을 확인한 뒤 하위 항목을 한 번 클릭한다.
TCG guest는 호스트에 배정된 CPU 범위에서 최대 4개를 사용하고 실제 호스트·guest CPU 수를 기록한다.
ARM 그래프 적용과 Ubuntu 종료의 실검증은 해당 대상의 최종 결과로 판단한다.
Linux 종료 관찰은 macOS Quit 명령과 같은 150초 한도에서 실제 편집기·controller 종료를 확인하고
걸린 시간과 남은 프로세스를 기록한다. 제품은 수락한 작업과 오디오 마무리를 기다린 뒤 종료하며
5초 종료 계약은 없다. 신호를 반복하거나 강제 종료해 통과시키지 않는다.

[GitHub가 재현한 macOS 15 Intel의 HTTP/3 전송 단절](https://github.com/actions/runner-images/issues/14924)은
Apple 공증 확인의 연결 단절(-1005)과 일치한다. 이전 전체 실행의 macOS 15 ARM에서도
새 설치 전체 통과 후 baseline PKG 검증의 세 번 모두 같은 연결 단절이 발생했다.
따라서 hosted macOS 15의 양쪽 CPU에 같은 TCP 경로를 적용한다.
검증 구간에만 전용 packet-filter anchor로 UDP 443을 차단해
HTTPS/TCP를 사용하고, 원래 규칙은 보존한다. 추출 전에 임시 규칙과 자신이 연 enable 참조를 해제하며
원시 명령·해제 결과를 보존한다. 서명·Gatekeeper·Apple ticket 검증과 해제 성공은 계속 필수다.
[실제 Intel 진단 40077145475](https://github.com/mixrelay/mixrelay/actions/runs/40077145475)은
새 설치·baseline·업그레이드의 Apple 검증과 임시 규칙 해제를 모두 통과했다.
다만 새 설치 26,312프레임, 업그레이드 18,548프레임 누락으로 오디오 연속성은 실패했다.
양쪽 시스템 캡처·녹음·UI·제거는 통과했다. PCM 변환 단계 계측은 최대 0.134097ms였으나,
별도 직접 렌더링 계측에서는 새 설치 구간의 시간 예산 초과가 두 번 기록됐다.
같은 구간 CoreAudio의 마감시간 초과와 입력·출력 콜백 시각 단절도 기록됐다.
백그라운드 GUI 측정 프로그램은 유한 I/O 구간에만 지연에 민감한 활동임을 OS에 알리도록 보완한다.
활동 토큰은 I/O 종료 후 해제하며 신호 길이·PCM 판정은 유지한다. App Nap이 누락의 원인인지는
이 기록만으로 확정하지 않는다.
[후속 진단 40078730846](https://github.com/mixrelay/mixrelay/actions/runs/40078730846)은
활동 보호를 기록했지만 Intel의 새 설치·업그레이드 오디오가 계속 실패했다.
새 설치 실패 직후 4코어 호스트에서 영상 인코더 `VTEncoderXPCService`의 CPU 사용률 96%와

양쪽 PCM 누락·반복·손상·비유한 값과 입력·출력 콜백 시각 단절은 0이었다.

시스템 iconservicesagent의 연속 충돌 17회·Abort trap 6을 확인했다.
[GitHub 러너 이미지 문제 14751](https://github.com/actions/runner-images/issues/14751)와 같은 증상이다.
시험 도구는 이 조건을 모두 확인한 폐기형 hosted VM에서만 해당 에이전트를 해제한다.
해제 상태와 native 아이콘 조회의 복구를 다시 확인하며 실패하면 시험도 실패한다.
이때 시스템 fallback 아이콘을 사용한다. TCC 승인과 실제 오디오 검사는 그대로 수행한다.

macOS 15 Intel에서는 PKG 서명·Gatekeeper 확인 뒤 Apple stapler의 연결 단절(-1005)이
세 번 모두 발생했다. 제품 시험 전 실패로 보존하며 검증을 생략하지 않는다.

[이전 Ubuntu ARM 실행](https://github.com/mixrelay/mixrelay/actions/runs/40066104242)은 부팅과 두 설치 모드의
설치·실행·저장·녹음·제거를 통과했으나 이전 UI 시험과 업그레이드 PCM에서 실패했다.
Linux 시험은 같은 4초 신호를 쓰면서 재생 프로세스를 3초 뒤 중단해 TCG의 늦은 시작을 잘랐다.
이제 캡처의 첫 PCM과 유한 재생의 실제 drain을 기다린다. 데이터·채널·레벨 판정은 유지한다.

## 진단과 전체 수락의 구분

HAL 수정이 포함된 이전 소스 `79d0f67b`의
[macOS 27 ARM 진단](https://github.com/mixrelay/mixrelay/actions/runs/40068585053)은
새 설치·업그레이드의 필수 시나리오와 제거를 통과했다. 양쪽 PCM 누락·반복·손상·비유한 값은 0이었다.
화면 캡처 파일에는 빈 앱 본문이 찍혀 있어 이 이미지로 렌더링의 적합성을 판정하지 않는다.
실제 클릭·접근성 트리·저장된 그래프와 오디오 결과를 시각 확인과 구별한다.

[Kali x64 진단](https://github.com/mixrelay/mixrelay/actions/runs/40068112836)도 두 설치 모드를 통과했다.
두 실행은 일부 대상을 선택한 진단이므로 누락 대상을 실패시키는 전체 inventory는 통과하지 않는다.
이 결과를 현재 후보의 전체 통과로 승계하지 않는다.

이전 [1e513f21 후보](../2026-10-24-1e513f2/README.md)의 실패와 원시는 보존한다.
macOS 최소 지원 버전은 process tap API에 따른 14.2다. 정확한 14.2에서 실검증했다고 주장하지 않는다.
실행이 관측한 실제 패치·CPU·파일 해시를 보존하며, 지원 정책은
[제품 문서](../../../product.md)와 [지원 계약](../../../../support/environments.json)을 따른다.

문서는 `docs` 설정으로 교정했고 변경 산문의 문장부호 정규화는 변경 없이 끝났다.
초기 후보 기록 갱신의 보존 검사는 제품 문서 3개, 검증 현황 2개, 플랫폼 인벤토리 2개 오류로 실패했다.
후보 식별자·링크·상태표 갱신이 원인이며, 확인한 빌드와 실행에 대조해 변경 범위를 검토했다.
이 결과를 기계적 보존 검사 통과로 표시하지 않는다.
이전 후속 기록의 보존 검사도 표·시험 커밋·실행 링크 갱신에 따른 3개 오류로 실패했다.
갱신한 값은 각 실행의 실제 소스와 결과에 대조했다.
