## Linux 명령 처리와 관찰

Linux 장치·앱 검색은 동기식 자식 프로세스를 기다렸다. 이를 비동기 명령 처리 안에서 직접
실행하면 다른 제어 작업과 해당 요청의 생존 응답까지 멈췄다. 기존 시간 제한이 있는 검색을
별도 작업 스레드로 옮겼으며, 수락한 검색은 종료 시 완료를 기다려 자식 프로세스를 회수한다.
동일한 단일 스레드 런타임에서 검색과 독립 제어 작업을 함께 실행한 회귀 시험은 변경 전에
응답하지 못해 실패했고 변경 뒤 통과했다. 비동기 읽기 취소와 변경 명령 재전송 금지는 유지한다.

AT-SPI 초점 요청의 응답이 누락되면 관찰기는 캐시를 갱신한 실제 초점 상태를 확인한다.
초점을 확인한 경우에만 Return을 한 번 보내며 초점 요청은 반복하지 않는다. 초점이 없으면
기존 관찰 제한 안에서 실패한다. 이 회귀 시험도 변경 전 실패·변경 후 통과를 확인했다.
녹음 준비·녹음 오류 검사와 설치본 UI 수락 조건은 유지한다.

로컬 데스크톱 시험 237개(제외 0개), 엄격 clippy, 크레이트 계층 검사, E2E 도구 시험 160개,

작업 회수의 회귀 시험이 통과했다. 실제 설치본 확인은 위 전체 실행의 최종 inventory로 판단한다.

## 전체 실행의 실패와 후속 부팅 확인

macOS 15 ARM 업그레이드는 PCM 누락·손상 각 608프레임, 15 Intel 새 설치는 누락
17,636프레임, 26 Intel 업그레이드는 누락 11,996·반복 2,752·손상 6,272프레임으로
실패했다. 이 세 대상의 나머지 시나리오와 정리는 통과했다.

Debian ARM 업그레이드는 Recorder 준비에 실패했다. 실제 창의 진단에는 로컬 엔진 연결 오류와

통과했지만 업그레이드 기준 설치본의 Driver가 SIGKILL로 종료돼 후보 설치에 도달하지 못했다.
기존 journal은 종료 신호를 기록했으나 발신자를 확인하지 못했다.

Ubuntu ARM은 EFI 마운트 지연 뒤 원래 마운트 복구를 완료했지만 cloud-init 설정·최종 단계와
SSH가 시작되지 않아 설치 전에 중단됐다. 시험 도구 소스 `8c85aeb1`은 정상 부팅 전환과
cloud-init 후속 단계의 시작을 요청한다. [후속 VM 준비 실행](https://github.com/mixrelay/mixrelay/actions/runs/40114749697)은
7개 환경 모두 통과했다. 이때 Ubuntu ARM은 비상 부팅에 진입하지 않았으므로 해당 실행만으로
복구 분기가 실환경에서 검증됐다고 판단하지 않는다. 설치본 실패 판정도 유지한다.

전체 설치본 실행의 실패 상태는 PR 소스 커밋에도 기록했다. 전체 실행은 같은 상태를 자동으로
갱신하며, 일부 대상만 고른 진단은 전체 지원 계약의 통과 상태를 만들지 않는다.


## 같은 설치본의 후속 전체 실행

시험 소스 `a9b002d539663be84c98ff34310df3d175867c31`의 [전체 실행 40155560097](https://github.com/mixrelay/mixrelay/actions/runs/40155560097)은

제품 소스와 네 설치 파일은 위 `a78e85ef` 후보 그대로이며, 준비 단계가 제품 소스 일치를 확인했다.
[이번 원시 inventory](full-inventory-a9b002d.md)를 앞선 실행과 합산하지 않는다.

Ubuntu ARM은 신규 설치와 업그레이드의 모든 필수 시나리오를 통과했다. 이때 비상 부팅은
발생하지 않았다. 별도 집중 실행 `40151814171`에서는 신규 설치의 Recorder 준비가 실패했고
업그레이드는 통과했으므로 UI 간헐성은 해결되지 않았다. Arch는 두 설치 경로를 통과했고,
신호 추적에서 Driver의 SIGKILL은 재현되지 않았다. 이전 강제 종료의 원인은 미확인이다.

Debian ARM은 업그레이드의 Recorder 준비가 다시 실패했다. 실제 진단 화면에는 로컬 엔진
연결 오류와 자동 적용 중지가 표시됐지만 오디오 세션과 Driver는 준비 상태였다. 나머지
필수 시나리오와 정리는 통과했다. 응답의 상태·오류 코드·수락 결과를 구별하는 집중 진단을
추가했다. 이 추적은 UI 검사 뒤 종료하고, 전체 수락 실행에서는 사용하지 않는다.

macOS PCM은 14 ARM 업그레이드에서 누락·손상 각 128프레임, 15 ARM 업그레이드에서
각 940프레임, 15 Intel 신규 설치에서 각 672프레임·업그레이드에서 각 892프레임,
26 Intel 업그레이드에서 각 868프레임이 발생했다. 반복·비유한 값은 모두 0이었지만
원래의 PCM 실패 판정은 유지한다. 제품 제거 후 같은 Mac들의 BlackHole 대조는 통과했다.
이전 독립 대조의 실패도 보존하며, 어느 결과만으로 러너 또는 제품을 단일 원인으로 확정하지 않는다.

macOS 27 ARM의 제품 시나리오는 모두 통과했으나 추가 BlackHole 대조는 Xcode 27이
기본 배포 타깃 10.10을 거부해 빌드 전에 중단됐다. 대조 빌드에는 배포 타깃 14.2를 명시한다.
대조 드라이버의 원본 리비전은 유지한다. 시험 소스 `8b09f9d3`의 집중 실행 `40164136327`에서
macOS 27 대조 빌드는 통과했으나 제품 신규 설치는 PCM 누락 660프레임, 제거 후 독립 대조는
1,024프레임 누락·128프레임 클라이언트의 클럭 단절 3회를 기록했다. 두 실패 판정은 유지한다.


[원시 PCM과 녹음 파일 대조](a9-recorder-gap-comparison.json)는 프로브의 결정적 신호를
동일한 스테레오 4프레임 창으로 찾아 비교한다. 위 전체 실행의 다섯 PCM 실패 측정에서
프로브가 잃은 신호 구간은 앱 녹음에서도 확인되지 않았다. 경계의 4프레임 미만 구간에서는
검출하지 못할 수 있으므로 녹음의 정확한 손실률로 사용하지 않는다. 이 대조는 출력 전달 경로를
조사할 근거이며, HAL·CoreAudio·러너 중 단일 원인을 증명하거나 기존 판정을 바꾸지 않는다.

집중 진단의 `macos_scheduler_trace`는 Apple System Trace의 시스템 전체 기록이 시작된 뒤
새 설치의 기존 단일 프로브를 실행하고, 측정 종료 후 기록을 마친다. 신호·재생 횟수·버퍼·PCM
수락 조건은 유지하며 별도 파일에 추적을 남긴다. 추적의 부하는 진단 자체에 영향을 줄 수 있다.
전체 수락 실행은 이 옵션과 `linux_control_trace`를 모두 거부한다. Linux VM의 시나리오 출력은
원시 로그와 실행 중 콘솔 양쪽에 남긴다.

집중 실행 `40166049744`에서 Debian ARM과 Ubuntu ARM은 모두 신규 설치의 Recorder 준비에
실패했고 업그레이드는 통과했다. 나머지 필수 시나리오와 정리는 모두 통과했다. 신규 설치 로그에는
편집기와 Driver 런타임 사이의 응답 시간 초과가 반복됐다. 당시 추적은 소켓 전송의 `sendto`를
포함하지 않아 오류 응답이 없었다고 판단할 수 없다. 추적은 이 호출과 `sendmsg`를 포함하고,
성공 응답을 포함한 숫자 상태별 관측 수를 함께 남긴다.

macOS 15 Intel의 집중 실행 `40166804478`은 신규 설치에서 PCM 누락 4,748프레임,
업그레이드에서 2,088프레임으로 실패했다. 정리는 모두 통과했다. 당시 System Trace는
LaunchServices의 `open` 프로세스만 기록했고, 프로브의 PCM 측정이 시작되기 전에 끝났다.
이 기록으로 CoreAudio 콜백의 스케줄링 원인을 판단할 수 없다. 이후 추적은 시스템 전체를
기록하며 기존 측정의 시작과 종료를 포함하도록 수명을 관리한다.

시험 소스 `2d987f96`의 집중 실행 `40191989039`에서 Debian ARM은 신규 설치와 업그레이드의
모든 필수 시나리오와 정리를 통과했다. 두 UI 추적은 각각 일시적인 `node_not_found` 응답 한 건을
기록했고 이후 UI 조작이 완료됐다. 이 결과만으로 앞선 연결 오류나 간헐성이 해결됐다고 판단하지 않는다.
같은 소스의 VM 준비 실행 `40191965838`은 7개 대상을 모두 통과했다. Ubuntu ARM의 비상 부팅
복구 분기는 이번에도 실행되지 않았다.

macOS 15 Intel 집중 실행 `40191991188`은 신규 설치의 PCM 누락 420프레임으로 실패했고
업그레이드는 기준 PKG의 CloudKit 티켓 조회 오류 65로 설치 전에 막혔다. 정리는 모두 통과했다.
기준 PKG의 서명과 Gatekeeper 검증은 통과했다. 같은 SHA-256의 파일을 로컬에서 읽기 전용으로
`stapler validate -v` 검증한 결과도 성공했으나, 실패한 러너의 상세 응답은 확보하지 못했다.
티켓 검증은 상세 응답을 보존하며 오류 65를 계속 거부한다. PCM 추적은 기준 설치 전제 단계에
앞서는 신규 설치의 기존 측정 한 번에 적용한다. 이 실행에는 업그레이드 PCM 추적 증거가 없다.
