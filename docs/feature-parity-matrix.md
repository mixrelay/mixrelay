## 판정 규칙

- 작업 순서 확정: 기존에 합의한 동작을 macOS·Windows·Linux에서 먼저 구현·검증한다. 미정 사항은 보류 목록으로 분리하고 확정 범위 완료 뒤 결정한다. 미정 항목 논의를 이유로 현재 구현을 멈추거나 새 기능을 추가하지 않는다.
- 열린 출시 게이트 수는 미구현 기능 수가 아니다. 기존 요구의 실제 누락·OS별 구현 차이·검증 부족·범위 검토를 구분하며, 새 기능을 완료 조건에 암묵적으로 추가하지 않는다. 2026-09-07-agreed-behavior-audit.md 참고.
- implementation은 실제 동작 코드의 존재, verification은 확보한 증거 종류다. 컴파일 성공은 implemented/native_device로 승격시키지 않는다.
- P0/P1는 issue가 closed이고 모든 applicable OS가 implemented이며 requiredVerification 이상이어야 출시 게이트가 닫힌다. 열린 항목이 있으면 전체 완료 선언을 금지한다.
- 기존 validation 문서는 검증 이력의 위치이지 현재 구현 정답이 아니다. source/test 경계와 함께 검토하고 변경 뒤 영향 범위를 재검증한다.
- source/unit/component 결과와 native_fixture/native_device/production 증거를 분리한다. 이 JSON은 실험 로그를 대체하지 않으며 coordinator 보고는 note에 표시한다.
- owner/issue는 내부 관리 추적이다. 담당 배정 또는 in_progress가 구현 완료를 뜻하지 않는다.
- 플랫폼 전용 플러그인 형식은 not_applicable로 구분하되 공통 제품 기능은 OS 차이를 이유로 자동 제외하지 않는다.
- Linux는 배포판별 검증 증거를 공유 완료로 복제하지 않는다. 미확인 설치/접속 상태는 unknown이다.

검증 순서: source → unit → component → native_fixture → native_device → production. 이는 증거 종류의 순서이지 기능 완성도 점수가 아닙니다. native_fixture는 실제 API를 사용한 합성 장치/테스트 플러그인; native_device도 물리 64채널 인터페이스나 장시간 방송 합격을 자동 의미하지 않습니다.
